# 工程教训（2026-11-15 夜）

> 这一晚从 20:00 调到 05:00，大部分时间花在三个"自造中间层"上。
> 记录原因，避免下次在同一个坑里再花四小时。

## L1 引擎已有的权威数据源，不要用采样重建去替代

**案例**：位移。

最初的做法是「烘焙片段步速表（`KawaiiMotionProfile`）→ 运行时按表算速度 → 用 `moveSpeed / strideScale / accelTime / decelTime` 去逼近」。
实测：身体走 5.29m 时，着地脚仍在世界坐标里移动 3.52m（**67% 滑步**）。
换成 `applyRootMotion` + `OnAnimatorMove` 转交位移，代码约 50 行，滑步问题当场消失。

**为什么手搓一定不准**：把动画曲线压成一个标量速度，丢掉了两个维度——**循环内步幅的逐帧变化**和**相位**。
参数调到哪个值都只能对齐其中一段，其余必然滑。这不是调参问题，是模型缺自由度（见 L4）。

**教训**：先问"引擎有没有权威来源"（root motion、`AnimationCurve`、`Rigidbody` 速度），有就别自己采样重建。
手搓只在"权威来源不存在"或"需要跨端同步而必须代码驱动"时才成立——而那时也应该用**动画跟随速度**（cadence matching），不是反过来用速度逼近动画。

## L2 中间层必须能被逐帧验证

`KawaiiMotionProfile` 的问题不只是不准，而是**没法验证**：它是构建期烘焙的静态表，运行时无法回答"这一帧应该走多远"。
所以每次不对，只能改参数再跑一遍——一轮 3 分钟，一晚几十轮。

对比 root motion：`animator.deltaPosition` 每一帧都是权威值，`rm_stall` 快照能直接读出 `deltaPos / velocity / rootPos`，一次就能定位到"片段播完钳在末帧"。

**教训**：中间层要么能被逐帧校验，要么别造。不可观测的抽象层会把调试成本放大十倍。

## L3 诊断前先确认"你看到的就是玩家看到的"

**案例**：构建器 `Shoot()` 拍预览图会临时移动主相机，拍完忘了恢复。`SaveScene` 在 `Shoot()` 之前，于是**磁盘场景是对的、内存场景是脏的**——构建完直接 Play，视角停在"窗边朝门口看"的机位。

后果：连续几小时把"她在窗边踱步""过不来"当成玩法问题，还因此搬了两小时家具（椅子、靠垫、床）。
真相是：`Walk` 片段 `loopTime` 没写进 `.meta`（播一遍就停）+ 当时还没有栅格 A*（手写锚点边穿过床）。

**教训**：出现"数据和画面不一致"时，先验证观测链路（相机是不是玩家的、日志字段是不是它声称的那个），再查业务逻辑。
顺带一条：日志里 `Camera.main` 不等于"玩家相机"——场景里有 58 个相机时它会骗人，应该直接记录组件引用。

## L4 同一个参数调了三次还不准，问题就在模型，不在参数

今晚反复出现的模式：

| 现象 | 反复调的东西 | 真正的缺失维度 |
|---|---|---|
| 滑步 | `moveSpeed` / `strideScale` | 逐帧位移（应读 root motion） |
| 起步"猛" | 混合时长 0.15 / 0.30 | 两段片段的根偏移不闭合（与窗口无关） |
| 走路卡死 | `forced_idle` / `forced_walk` / 探针 | 片段没有循环 |
| 过不来 | 搬床、搬椅子 | 导航器不够强 + 片段不循环 |

**教训**：调参调不动时，先问"我这个模型有没有少一个自由度"。少一个自由度，任何参数组合都只是在对齐不同的错误。

## L5 换掉机制之后，剩余问题会回到机制本身的"文档化行为"

切到 root motion 后，剩下的问题变成了 `loopTime` 没写、`CrossFade` 的时长是归一化时间、过渡默认 `hasFixedDuration=false`——全是 Unity 有文档、有先例的行为。
而在自造方案里，剩余问题是你自己发明的语义，只能靠试。

**教训**：这类"剩下的坑"在哪一层，是判断方案好不好的实用标准。优先选"剩下的是别人踩过、有文档的坑"。

## 一句话

> 能借轮子就别手搓；手搓要能逐帧验证；调三次不准就换模型；先确认眼睛没坏。
